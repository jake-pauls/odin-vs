# Debugger extensibility via Concord (VS 18.11, verified in an Exp instance)

Concord is the debug engine extension API. Use it when natvis cannot do the job (slices, computed lengths, renaming types, translating Watch expressions, decoding runtime structures like maps). Findings from the Odin visualizer spike (`spikes/concord-visualizer/FINDINGS.md` in odin-vs). Take evidence from the user running Exp; a build and install prove nothing.

## Setup that works
- A VSIX asset `Type="DebuggerEngineExtension"` pointing at a compiled `X.vsdconfig`; the spike started as a separate VSIX and was then merged into a copy of a product VSIX and ran alone (see "Merging into a product VSIX"). In-proc, loaded into `devenv` on the first debug event, level `9992100` for IDE-side components.
- Packages: `Microsoft.VisualStudio.Debugger.Engine` and `Microsoft.VSSDK.Debugger.VSDConfigTool` (17.14.x worked on 18.11), `Microsoft.VSSDK.BuildTools`. net472 (no C# `record`/init: `IsExternalInit` is missing).
- Author `X.vsdconfigxml`; the tool writes `bin\...\X.vsdconfig`, which is NOT put into the VSIX automatically: add it as `<Content ... IncludeInVSIX=true>` and check the zip.
- Interface filters pick when you are called, e.g. `<LanguageId RequiredValue="DkmLanguageId.C"/>` on `IDkmLanguageExpressionEvaluator`. Native-PDB languages without their own compiler id (Odin) show up as language C with an empty module `CompilerId`. The component then sits in front of every language-C frame (MSVC C code as well as Odin), not C++ frames; scope it with a module gate before shipping (see "Merging into a product VSIX and scoping").
- Exp install order: stop Exp, install the VSIX, `devenv /rootSuffix:Exp /updateconfiguration`, launch; bump the manifest version each time. Log to a file (`%LOCALAPPDATA%`); the component is silent otherwise.
- The debuggee's exe is locked while debugging: rebuild the sample only after stopping.

## Merging into a product VSIX and scoping (verified in Exp)
- A component merges as: DLL and compiled `.vsdconfig` inside the VSIX, `<Asset Type="DebuggerEngineExtension" Path="X.vsdconfig" />`, a `vsdconfig` content type. When hand-patching a BUILT VSIX copy: the built `extension.vsixmanifest` has no `d:` namespace (do not copy `d:Source`), `manifest.json`/`catalog.json` are required and must carry the new version and files, and the version must change or the installer ignores it. `VSIXInstaller /quiet /rootSuffix:Exp /uninstall:<Identity Id>` works in Exp (exit 1002 = not installed).
- The `LanguageId` filter is per frame: MSVC C++ frames report C++ and never reach a language-C component, but MSVC C frames do. `DkmModule.CompilerId` is all zeros for both MSVC and Odin modules, so it is no gate. A working gate is a cached per-module check of the symbol file (`module.GetSymbolFilePath()`, IDE component only) for a language-specific byte string such as `.odin`; pass every `IDkmLanguageExpressionEvaluator` method through for other frames.
- A global natvis entry named like a common type (`string`) also changes unrelated C++ types of that name; scope such display in the component, behind the gate.
- Click-only automation of Exp works: a `__debugbreak()` in the sample stops the session without a breakpoint; the Start/Continue/Stop toolbar buttons and the Locals tab can be clicked and read from screenshots.

## Chaining and replacing results
- You sit in front of the native evaluator: call the same method on the first-parameter object (`inspectionContext.GetFrameLocals/EvaluateExpression`, `result.GetChildren`) to get its results, then return your own or modified ones. Pass-through alone looks normal to the user.
- Replacing a result: `DkmSuccessEvaluationResult.Create` with your own type/value; attach a `DkmDataItem` (looked up by exact type via `GetDataItem<T>()`) to route later `GetChildren`/edit/underlying-string calls back to the original. Wrap enum contexts to transform children lazily. `DkmGetChildrenAsyncResult` enum context counts all children, initial ones included; the initial children can be just a few synthetic ones with the rest produced by your own enum context's `GetItems`.
- Synthetic children (`[len]`, `[cap]`, map entries `[key]`) are plain `DkmSuccessEvaluationResult`s you create; entries whose value should stay expandable are rebuilt from the native result with a new name and a `RetypeData`-style data item pointing at the original.
- Results from the C++ EE usually have no `Address`, so read what you need with your own evaluations (`<name>.data`, `<name>.len`), then `inspectionContext.RuntimeInstance.Process.ReadMemory(address, DkmReadMemoryFlags.None, buffer)` for raw memory.
- The C++ value text is truncated (`len=...`) when long: do not rely on parsing it; evaluate the member.

## Evaluating through the native evaluator
- Build the expression text yourself and call `inspectionContext.EvaluateExpression` with a `DkmLanguageExpression` carrying a marker data item; your own `EvaluateExpression` passes marked expressions straight on so they are not rewritten again. Results of marked expressions are raw (not transformed by you).
- `sizeof(x.data->member)` gets a member's size without naming its type (anonymous or odd type names cannot be spelled in a cast).
- Casts `*(T*)0xaddr` work for plain names but not for names the C++ parser reads as a scope. In Odin, `main::Thing` fails because `main` is also a function; a leading global-scope `::` (`*(::main::Thing*)0xaddr`) works, also for proc-local types like `main::main::Triple::$585`.
- A natvis-like `expr,N` array view (`<name>.data,<len>`) gives native element display and expansion for free.

## Threading and re-entrancy (cost three Exp crashes/hangs)
- A call to `inspectionContext.EvaluateExpression` made from inside a completion callback of the same method is treated as a further chain step. Two levels deep worked; the third never answered (modal "Evaluating expression..." for 30 s+, VS killed).
- Do NOT work around it with thread-pool threads or timers: an exception escaping such a thread kills `devenv`, `DkmLanguageExpression.Create` with a data item threw `DkmException: Error in the application` off the dispatcher, and completing an evaluation from your own thread never reached the UI (a watchdog fired ~14,000 times with no effect). `DkmComponentManager.InitializeThread` did not fix it.
- What works: stay on the dispatcher's callbacks, never nest deeper than two, and when you need several attempts issue them as one flat batch from the first callback (count completions with `Interlocked`, answer from the last callback). This is also how to try alternatives (all subsets of `.data` insertions for Watch indexing, several cast spellings) and how to fetch several header values at once.
- Skip extra evaluations when the call is already two deep (the Watch fallback path); a missing optional detail is better than a hang.

## Limits seen
- You can retype scalars (`__int64` as `int`) but the PDB cannot tell `int` from `i64`, or `[^]T` from `^T`.
- Display customization is per component and per language filter, so scope by language/module to avoid touching C++ debugging.
- Autos was empty for `.odin` with and without the component (no language service); not fixable from a debug component.
- Package-level variables are only reachable in Watch, and only if the compiler emitted a symbol for them.
- Anything decoded from a runtime's own memory layout (Odin maps) breaks silently when the language runtime changes: list it, and test it against the installed toolchain (a source check plus a layout dump compared with the decoding math).

## Display recipes that worked (Odin: slices, maps, unions, matrices, strings)
- **Replace a container's value text and children:** create your own `DkmSuccessEvaluationResult` with `Expandable | ReadOnly` flags and a data item; answer `GetChildren` from the data item. Pseudo children (`[len]`, `[cap]`, `[storage]`) and synthetic row/entry results use a `FullName` of null or a derived expression; an enum context over a plain list is just a data item whose `GetItems` slices the list.
- **Show a variant instead of the whole struct (Odin `union`):** the C++ value text is `{tag=N v1=... v2=...}`; match the never-cut prefix (`^\{tag=\d+ v\d+=`), evaluate the active member (`<name>.v<N>`) in the shared batch, and return a result whose value is that variant's text and whose `GetChildren`/edit forward to the variant result (`RetypeData`). Tag 0 is `nil`.
- **Storage order and padding from the PDB name:** Odin writes `#row_major matrix[2, 3]f32` into the PDB type name (column-major is the default and has no prefix), and the `data` member is `float[cols][rows]` / `float[rows][cols]` with no padding in practice. Evaluate `<name>.data[c][r]` (or `[r][c]`) for all cells in one batch and format rows yourself.
- **Strings (a `{data, len}` pair):** read the header from memory when the result has an `Address`, else evaluate `.data` and `.len`, then `ReadMemory` the bytes by length (no NUL), UTF-8 decode, escape, cap at 256 bytes. For anything you already know the address of (map keys and values) read memory directly: it needs no evaluation, which matters because of the nesting limit.
- **Never take a container length from value text.** The text is cut off, and when an element type stops being rendered by natvis the text of a map or of a slice of structs contains the `len=` of nested members, so a right-to-left `len=` search returned a nested string's garbage length (`len=68169720922112`). Evaluate `<name>.len`. Removing a natvis entry changes the text of everything that contains that type: re-run every display after such a change.
- **One failure must not drop a batch:** a garbage length (`-1`) made one parse throw and the catch discarded every result of the batch (unions in the same Locals refresh stayed unconverted). Parse and fall back per item; log the odd one.
- **A byte search of a PDB for a language marker is only as good as its pattern.** Real Odin PDBs hold the path as NUL-terminated bytes (3 copies each) and also `[file.odin]` inside symbol names: match `.odin` plus a NUL, cache only definitive answers (a missing or locked PDB is "try again next frame"), and stop at the first match without capping the file size (a cap silently disables the display for a big Odin PDB; measured 0.4 s per GB warm, several seconds cold, only a big non-Odin module reads it all). No thread is allowed (see the re-entrancy rules), so log a warning when a scan is slow.
- **Zero-sized map values (`map[K]struct{}`):** Odin's cell for a zero-sized type is 0 bytes (no values array), so decoders must not round it up to a cache line; entries cannot be cast to `struct{}`, show the key only. A real-layout dump test found this; the formula tests alone did not.
- **Per-frame decisions are cheap if cached:** `module.GetSymbolFilePath()` plus a byte search of the PDB took 1 to 2.5 ms once per module.

## Testing decoders that depend on a runtime layout (verified)
- Put the math in a plain library (no Dkm types) and test it: unit cases, a source check, and a layout dump.
- **Source check:** read the installed toolchain's own source and assert, whitespace- and comment-insensitively, the exact constructs the decoder assumes (struct field order, constants, key lines of the indexing procedures). The failure message names the decoder to update.
- **Layout dump:** a small program in the debuggee's language that asks the runtime itself (`runtime.map_kvh_data_dynamic`, `map_cell_index_dynamic`, `map_info`, `map_hash_is_valid`) where each piece lives, for many key/value sizes, growth and deletions, printing parseable lines; the test runs it (`odin run -file`) and compares every number with the library. A deliberate mutation of the formula must fail both (check once).
- The manual debugger checklist stays the third layer: PDB spellings (`#row_major matrix`, `tag`/`v<k>` union members) are compiler output, not source, and only a debug session shows them.

## Driving the debugger session from automation
- A sample with `__debugbreak()` (C/C++) or one preset breakpoint stops without keyboard input; Locals needs no typing. With click-only computer use: Start, Continue, Stop, the Locals tab and expand arrows work; the break dialog "Breakpoint Instruction Executed" can stay up and swallow the first Continue (click Continue again).
- Odin builds from F5 only when `odin.exe` can overwrite the exe: a still-running debuggee or an open debug session gives "Error(013) can't overwrite"; stop the session (and kill a stray process) first. `odin check` verifies source without touching the exe.
- C/C++ control projects build with VS MSBuild directly: a hand-written `.vcxproj` with `PlatformToolset` `v145` (VS 18.11 toolset folder `MSBuild\Microsoft\VC\v180\Platforms\x64\PlatformToolsets`) and `Application` type built with `MSBuild.exe -p:Configuration=Debug -p:Platform=x64`.

## Shipping a component inside a product VSIX (odin-vs promotion, 2026-11-09)
- Make the component its own net472 project (Microsoft.VisualStudio.Debugger.Engine + Microsoft.VSSDK.Debugger.VSDConfigTool, VsdConfigXmlFiles item), reference it from the VSIX project with a plain ProjectReference (build order and the dll in the container), and include the compiled config as a Content item with IncludeInVSIX: `..\Comp\bin\$(Configuration)\net472\Comp.vsdconfig`. Add one manifest asset: <Asset Type="DebuggerEngineExtension" Path="Comp.vsdconfig" />. No Assembly asset was needed; the container gets the vsdconfig content type from the build.
- The class names in the .vsdconfigxml must match the namespace and a public class with a public default constructor; a mismatch fails silently (the component is never constructed), so log in the constructor and test the names against the source.
- Keep an unfiltered registration (NoFilter) out of a shipped component: it runs for every debuggee.

## Watch expressions and lookups (odin-vs G9, 2026-11-10, verified in Exp 18.11)
- **Rewrite typed text in `EvaluateExpression`, and give the native evaluator the typed form together with probes in ONE flat batch** from the entry call. The probes are only used if the typed text fails. A second stage may run from that batch's callback (two levels total); never a third.
- **Results of a batched `EvaluateExpression` (TreatAsExpression) have no `Address`.** Get an address by evaluating `(unsigned __int64)&(expr)` in the same batch and parsing the number; do not parse value text for numbers otherwise (it is cut off). Fetch `.len`/`.cap`/address "extras" for every candidate in the same batch so a string, slice or map can be decoded without a deeper evaluation.
- **VS saves Watch rows by `FullName` and re-evaluates it on the next session.** A result you build for a rewritten expression must carry the TYPED text as Name and FullName, or the row goes stale after a restart. Keep the evaluable text in your own data item (`EvalName`) and build children from that, not from `FullName`.
- **The C++ evaluator cannot spell a language's composite type names** (`[]int`, `map[K]V`, `[dynamic]T`) in a cast. When a value of such a type has to be shown (a map value that is itself a slice), read its header from memory with `ReadMemory` (you need the runtime's layout) and build the result and its children from that; a cast of the element pointer plus a length (`(T*)0xADDR,N`) gives native element display.
- **Bounds checks belong in the component:** the native evaluator happily reads past an array. Evaluate the index (`(__int64)(index)`) and the length in the same batch and answer a clear error naming the length.
- **A wrapper that answers exactly once** (an "answered" flag, `try`/`catch` in every callback falling back to the native result) keeps an exception from escaping into a Concord callback, where it can wedge or kill the session. A guard for text with side effects (assignment, `++`, calls) must disable probes and bounds checks so they are not run twice.
- **Debug info can give two distinct types one name.** The evaluator then resolves the name to one of them per run, so sizes derived from the name (`sizeof`) are right for one and wrong for the other, and which one flips between runs. Cross-check with a quantity the runtime stores itself (a container's own `len` against your scan) and report a mismatch instead of showing garbage.
- **Synchronous reads of debuggee memory are fine on the dispatcher thread** but put hard caps on every loop and buffer (bytes read, comparisons, slots) and say so in the message when one is hit.
