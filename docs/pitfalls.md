# Pitfalls

Verified problems and their workarounds. Add new ones with how they were verified.

## `Uri.LocalPath` breaks on ols file URIs
ols sends drive-letter URIs with the colon percent-encoded: `file:///D%3A/Projects/x/main.odin`. On .NET Framework `new Uri(uri).LocalPath` gives `/D:/Projects/x/main.odin`, and `File.ReadAllText` on that throws `System.NotSupportedException: The given path's format is not supported.`
Decode the URI yourself: `Uri.UnescapeDataString(uri.AbsolutePath)`, drop the leading `/` before a drive letter, swap `/` for `\`, and handle a non-empty `Host` as a UNC path. We had a tested helper for this (`FileUriPath`, removed again in the M2 branch once nothing used it; it is in commit `e0460c8`). Verified in the Exp instance on 2026-10-30 (log line `could not read /D:/Projects/...`).

## An exception in the diagnostics middle layer hides every diagnostic
`OlsMiddleLayer` sits between ols and VS. If `HandleNotificationAsync` throws before `sendNotification`, VS receives nothing: no squiggles and an empty Error List, while the log still shows ols publishing. The reshaping is therefore wrapped in a catch-all that logs and forwards the original. Keep any new reshaping inside that `try`, and catch `Exception` there, not just I/O exceptions. This cost several rebuild cycles on 2026-10-30 because the earlier catch covered only `IOException`.

## The Error List "Project" column cannot be filled from `publishDiagnostics`
`_vs_projects` (project name, context, identifier) is only converted for `VSDiagnostic` objects in VS's diagnostics broker (`RemoteDiagnosticsBrokerHelper.ConvertDiagnostics`, decompiled); that is the pull path (`textDocument/diagnostic`), which ols does not implement. With the package name added to each pushed diagnostic, the Error List Project column stayed empty (Exp, 2026-10-30, 0.2.11, log confirmed the package `main` was found). Not pursued further; revisit only if a project system supplies the project for `.odin` files.

## The Error List "Source" column is not the LSP `source` field
The Source column showed "IntelliSense" even when the middle layer set `source = "ols"`; the column is a VS category for language-server diagnostics. Setting `source` has no visible effect in the Error List, so it is not set. The Code column and the squiggle tooltip prefix do come from `code`.

## `&` does not wait for VSIXInstaller or devenv
`VSIXInstaller.exe` and `devenv.exe /updateconfiguration` are GUI-subsystem programs, so calling them with `&` in PowerShell returns before they finish. Launching Exp straight afterwards raced the install and left no Odin features (no `OnLoadedAsync` in `%LOCALAPPDATA%\OdinVS\odinvs.log`); a second launch happened to work, so we first worked around it with a launch, close, launch sequence. With `Start-Process -Wait` (as `scripts/exp-reinstall.ps1` does now) a single launch loaded the extension (observed twice, 2026-10-30). The race was suggested by a code review and fits this evidence; it was not proven in isolation.

## The Exp instance must be closed before reinstalling
The installer cannot replace the extension while an Exp `devenv.exe` holds it. The script asks Exp processes (matched by `/rootSuffix Exp` on the command line) to close, and force-kills them after 15 seconds. Unsaved edits to a sample open in Exp can otherwise end up in a commit, as happened with `broken/main.odin`.

## CPS reads `ProjectConfiguration` metadata unevaluated
`ProjectConfiguration` items whose metadata is computed (item transforms, `$([System.String]::...)`, even `$(Platform)`) show up as literal text in the Configuration Manager (`$([System.String]::C...`, `$(Platform)`), VS reports "Current solution contains unknown project configuration mappings", and Build is skipped ("Skipped Rebuild All"). `dotnet msbuild` evaluates the same expressions fine, so command-line builds and tier-3 tests pass. Found in Exp 18.11 on 2026-11-01 after the first M3 commit; the code came from the odin-targets-path spike, which had never been re-run in Exp after that change.
Fix: declare the items with literal metadata (`Debug|x64` and `Release|x64`, each conditional on `$(Configurations)`, in `Sdk.targets`). Consequence: custom configuration names are not shown in VS. Guarded by tier-3 test `ProjectConfigurationsAreLiteralDebugAndReleaseX64`. Whether a user-written literal `ProjectConfiguration` item in the `.odinproj` shows a custom name in VS is untested.

## A project that declares its own `ProjectConfiguration` items replaces the SDK's in VS
Observed in Exp 18.11 (2026-11-01) with `Sdk.targets` declaring conditional `Debug|x64` and `Release|x64` items: a project with `<Configurations>Debug;Profile</Configurations>` plus one literal `Profile|x64` item showed only `Profile` in the Configuration Manager (MSBuild itself evaluated Debug and Profile). A project with `Debug;Release;Profile` and a literal item for each showed all three, and a Profile solution configuration built it into `bin\Profile`. A project with `Configurations` set but no literal items still showed Debug and Release. So a custom configuration needs a literal item for every configuration the project should show; the reason (items from the SDK being ignored once the project declares any) is inferred from these runs, not from CPS source. See `docs/user-guide.md`, "Configurations".

## Hand-written pkgdef key names that fail silently (package autoload and UI context rules)
Found 2026-11-02 in Exp 18.11 while registering `OdinVSPackage` by hand in `src/OdinVS/odin.pkgdef`; nothing errored, the package just never loaded:
- The background-load value on `Packages\{guid}` is `AllowsBackgroundLoad`, not `AllowsBackgroundLoading` (the attribute property is spelled with "ing", the registry value is not). With the wrong name, an autoload request was logged in the activity log as "ignored because package does not support background loading".
- UI context rules live under `$RootKey$\UIContextRules\{guid}`, not `UIContext`. With the wrong key nothing was reported at all and the context never activated.
To see what VS did with a package, start Exp with `devenv /rootSuffix Exp /log <file>` (never pass the .sln path: VS overwrites it), close Exp so the log is flushed, and search it for the package GUID. VS's own pkgdefs under `Common7\IDE\CommonExtensions` are the reference for key names.

## Odin PDB types, natvis and what the debugger shows (M5, 2026-11-03)
Checked in Exp 18.11 with `tests/samples/DebugOdin`: `odin build -debug` PDBs let the native engine bind breakpoints in `.odin` files and show Locals. Composite types keep Odin names (`string`, `[]int`, `[dynamic]string`, `runtime::Context`); scalars are CodeView built-ins (`int` is `__int64`, `u8` is `unsigned char`), and natvis cannot rename them, so Odin-style scalar names would need a debugger extension (built as the M5.5 prototype: slices, dynamic arrays and scalar names now display, see below). `Raw_Slice`, `Raw_Dynamic_Array` and `Raw_String` exist in the PDB but variables are typed `[]T`.
- The product's `odin.natvis` covered `string` only (it was removed in the M5.5 promotion, 2026-11-09). natvis rejects `[]int`, `[dynamic]string` and every pattern tried (`[]*`, `*]int`, `*[]int`, `*`) as `Invalid type name`, so slices and dynamic arrays show raw `data`/`len` and `data` expands to the first element. Workaround in Watch: `values.data,3`. The prototype for a real fix is the M5.5 milestone. VS-side detail is in the `visual-studio-2026-extensions` skill (pitfalls, "Debugging").
- Dynamic array literals in samples need `#+feature dynamic-literals` at the top of the file.
- `DebugOdin` console windows close at once on Ctrl+F5 because the program exits; that is expected, not a failed launch.

## Odin facts found while prototyping the debugger visualizer (M5.5, 2026-11-04 and 05)
Verified in Exp 18.11 with `spikes/concord-visualizer/sample` (Odin dev-2026-10); details and logs are in `spikes/concord-visualizer/FINDINGS.md`. Items marked "Odin version" depend on the base library and are the first thing to re-check on an Odin bump (see the table "Odin-version-coupled code" in FINDINGS.md).
- **PDB type names:** the module's `CompilerId` is empty and frames report language `C`. Composite names are Odin-shaped (`[]int`, `[dynamic]string`, `map[int]string`, `bit_set[main::Flag]`, `matrix[2, 2]f32`, `any`); scalars are C names (`__int64`, `float`, `char32_t`, `unsigned char`, `char *`). The package separator is `::` in the PDB (`main::Thing`); Odin writes `main.Thing`. A proc-local type is `main::main::Triple::$585`, and the number changes between builds.
- **Indistinguishable in the PDB:** `int` vs `i64`, `uint` vs `u64`, `[^]T` vs `^T` (both `T *`). Any display of Odin scalar names is a best guess.
- **Slices and dynamic arrays (Odin version):** `Raw_Slice` is `{data, len}`, `Raw_Dynamic_Array` is `{data, len, cap, allocator}`; the PDB members are named `data`, `len`, `cap`, so `x.data[i]` and `x.len` work in the C++ expression evaluator while `x[i]` and `len(x)` do not.
- **Maps (Odin version):** `Raw_Map` is `{data, len, allocator}`. `data` is a pointer with log2(capacity) in its low 6 bits (capacity = `1 << (data & 63)`, pointer = `data & ~63`, the allocation is 64-byte aligned). Keys, values, then hashes are consecutive arrays of 64-byte `Map_Cell`s: an element of size `s` below 64 sits at `(i / (64/s)) * 64 + (i % (64/s)) * s`, one of size 64 or more at `i * roundup(s, 64)`. The next array starts at the offset of index `capacity`, which for sizes that do not divide 64 is inside the last cell (12-byte keys at capacity 8: 100 bytes, so values are not 64-aligned). A slot is used when its hash (`uintptr`) is non-zero and bit 63 is clear (bit 63 marks a tombstone). Entries come out in slot order, not insertion order. The C++ type of the `data` member is `struct{key, value, hash, key_cell, value_cell} *`, which gives key and value sizes via `sizeof(m.data->key)`.
- **The C++ expression evaluator and Odin names:** `*(string*)0xaddr` and `*(__int64*)0xaddr` cast fine, but `*(main::Thing*)0xaddr` is rejected (`main` is also a function, so `main::` is resolved as a scope inside it; "name followed by '::' must be a class or namespace name"). `*(::main::Thing*)0xaddr` with a leading `::` works, also for proc-local types. `main::g_ints` does not name a package variable either; use the plain name.
- **Package-level variables:** Locals never lists them; add them to Watch by plain name. A global that nothing references got no debug symbol (`identifier "g_count" is undefined`); after the same globals were assigned and printed in `main` they were visible, including one with a constant initializer. Most likely cause is that Odin emits no symbol for unreferenced globals; not isolated. Not fixable from a debugger extension.
- **Autos:** empty for `.odin` files with and without our extension (no language service to pick the variables on a line).
- **Long values are cut off:** the C++ value text of a result ends in `...` once it is long (`{data=... len=...}`), so a `len=N` parsed from the text can be missing; evaluate `<name>.len` instead.
- **Building a sample while Exp is debugging it fails:** `odin build` reports `Error(013): don't have access to write to ...exe` because the debuggee holds the file; use `odin check` to validate source, then rebuild after stopping.
- **A Concord component ships through three coupled pieces (M5.5 promotion):** the assembly, the `.vsdconfig` that `vsdconfigtool` compiles from the `.vsdconfigxml` into the component project's `bin\<Configuration>\net472\`, and a `DebuggerEngineExtension` asset in `source.extension.vsixmanifest`. `OdinVS.csproj` includes the `.vsdconfig` as a `Content` item by that path, so the project reference (which builds the component first) must stay; the dll needs no `Assembly` asset (the registered class names in the `.vsdconfigxml` are `OdinVS.Debugger.<Class>`, checked by `DebuggerComponentRegistrationTests`). A wrong class name or missing asset fails silently: the debugger just never loads the component (check `odinvs-debugger.log` for `OdinEvaluator constructed`).
- **A global natvis entry named like a common type changed unrelated types:** the old product `string` entry made a C++ `struct string {char* data; long long len;}` show as `"hello"`. Natvis is not scoped to a language or module, so Odin `string` display lives in the Concord component behind the Odin-module gate (a PDB containing `.odin`), and `odin.natvis` was removed at promotion (2026-11-09).
- **The Odin gate is a PDB search, not a compiler id:** `CompilerId` is all zeros for MSVC and Odin; a module mixing Odin and C counts as Odin. See `spikes/concord-visualizer/FINDINGS.md` Phase F.
## Editing files with CRLF line endings from scripts
Working-copy files are CRLF (autocrlf), so a PowerShell `String.Replace` with a `` `n `` multi-line search string matches nothing and changes nothing silently. Check `$t.Contains($old)` (throw if not) and use the file's own newline. Also: a replace of `Global` + newline in a `.sln` also hit `EndGlobal`; anchor on the whole line.

## Auto-close needs the view option, a numeric literal needs a guard (M5, 2026-11-03)
On VS 18.11 (Exp) `BraceCompletion/Enabled` was false on every Odin editor view (seen in the log: manager present, Enabled=False), so VS never started a brace session. Whether `language-configuration.json` or the provider alone would work once the option is on was not tested separately. `src/OdinVS.LanguageServer/OdinEditorFeatures.cs` holds the three pieces: `OdinBraceCompletionEnabler` (turns the option on and keeps it on), `OdinBraceCompletionProvider` (the pairs) and `OdinNumericLiteralGuard` (no completion list inside `1.5f`). Do not delete the enabler as dead code. The diagnostic method was: log the view option and manager state from a typing handler. (The author's own `visual-studio-2026-extensions` skill has the long write-up; it lives outside this repo.)

## Multi-caret and box selection follow VS, not us (M5, 2026-11-03)
With several carets VS does not auto-close `(` (its `AutoSurroundCommandHandler` only acts when every selection is non-empty), and box-selecting text and typing `{` wraps it badly and can raise `ArgumentOutOfRangeException`; the user saw the same wrapping in a C# file in Exp 18.11, and the code is VS's shared `BraceCompletionManager.TryAutoSurround`. Our editor exports are all scoped to the `odin` content type (`src/OdinVS.LanguageServer/OdinEditorFeatures.cs`), so this is VS behaviour we deliberately leave alone. The old global `odin.natvis` entry for `string` also matched a C or C++ type literally named `string`; that is why it is gone.

- **Smart App Control blocks freshly built binaries (found 2026-11-10; this was the rare Core test failure).** The failing test was `OdinMapLayoutTests.RealHeaderLayoutsMatchWhatTheVisualizerReads`: `odin run` built `layout_dump.exe` and then "Failed to execute command" (exit -1). The Windows event log (`Microsoft-Windows-CodeIntegrity/Operational`, events 3077/3033/3118 "Smart App Control Block Details") shows the cause: Smart App Control blocked `odin.exe` starting that exe at the same minute, and, in the same session, `testhost.exe`, `MSBuild.exe` and Exp's `devenv.exe` loading the new `OdinVS.Core.dll` and `OdinVS.ProjectSystem.dll` (symptoms: `dotnet test` dies with "An Application Control policy has blocked this file (0x800711C7)", Exp shows a package-load error and the log says `OnServerInitializeFailedAsync`). It is a Windows security feature that judges unsigned binaries; it blocks intermittently and then persistently for a build output. Do not try to bypass it. Check with `Get-WinEvent -FilterHashtable @{LogName='Microsoft-Windows-CodeIntegrity/Operational'} -MaxEvents 20`; a block means the user has to decide about the setting (turning it off cannot be undone without reinstalling Windows). The layout dump test now builds with `odin build` and starts the exe itself, retrying a refused start; that only helps the intermittent case. Keep the full `dotnet test` output of a failing run (the first line of the message names the cause) before rerunning.

- **Odin's debug info can give two map types the same name, and the C++ evaluator then picks one per run (found 2026-11-10).** In `ConcordSample`, `map[int]int` (`many`) and `map[int][dynamic]int` (`dyn_map`) both showed `map[int]int` with `sizeof(data->key)` 8 and `sizeof(data->value)` 8 in one run, and in the next run the sizes of `dyn_map` were right and those of `many` wrong (the log line `map lookup ...: map type ..., member types ..., sizes ...` shows it). With the wrong value size the hash array is read at the wrong address: 8 "used" slots for a map of 1 entry, and an `int` of garbage instead of the dynamic array. The map header's own `len` is the cross-check: if the scan finds a different number of used slots, the layout is not this map's. LookupMapEntry and GetMapChildren do that check and say so. Not fixable from the component (the name is the only handle the evaluator gives). Avoid two map types with the same key and similar names in one Odin program when debugging, or inspect the other one in Locals (which resolves the exact type).

## Project references in CPS (M6, VS 18.11, verified in Exp 2026-11-10)
- **Add Reference comes from two capabilities, not from code.** `ProjectReferences` enables VS's own `BuildDependencyProjectReferencesService`, the Reference Manager Projects tab (`VsProjectReferencesProviderContext`), solution build ordering and VS's circular-reference check; `DependenciesTree` adds the **Dependencies** node and the *Project > Add Project Reference...* command. The `ProjectReference.xaml` / `ResolvedProjectReference.xaml` rules come from VS's `MSBuild\Microsoft\VisualStudio\Managed\` folder, and the project must define `ResolveProjectReferencesDesignTime` and `ResolveProjectReferencesDesignTime2` (the resolved-reference rule calls the latter). Found by decompiling `Microsoft.VisualStudio.ProjectSystem.VS.Implementation.dll` and `...ProjectSystem.Implementation.dll` into the scratchpad.
- **VS's default `IValidProjectReferenceChecker` asks "not a valid reference for this type of project" for every Odin-to-Odin reference.** A checker exported with `[AppliesTo("OdinProject")]` and a higher `[Order]` that returns `Supported` for `.odinproj`/`.vcxproj` removes the prompt. VS's circular check runs afterwards, in `AddAsync`; its message names no cycle path.
- **A reference graph walked by recursive `MSBuild` task calls ends in `MSB4006` on a cycle, before any Odin code can describe it.** Passing the visited chain as a global property would give our message but makes MSBuild evaluate each project once per distinct path, which is exponential for layered diamonds. Fixed (2026-11-14, `m7/cycle-path`): the `OdinWalkReferences` task asks the referenced projects level by level through `IBuildEngine3.BuildProjectFilesInParallel` for `OdinGetNodeInfo` (which does not recurse), so the resolver sees the whole graph and reports `ODIN0102` with the path. Two details: calling `Yield()` before `BuildProjectFilesInParallel` crashes MSBuild (`MSB0001 ... state is actually Yielding`; the call blocks the request itself), and empty global-property dictionaries make the referenced projects inherit the caller's `Configuration`/`Platform` (tier-3 `TheGraphWalkPassesTheConfigurationToReferencedProjects`). Link references are built after the graph is resolved (`_OdinCompile` depends on `OdinBuildLinkReferences`), so a cycle that includes one should be reported by the resolver too (by reading the targets; no test builds a Link cycle).
- **Unqualified `%(Metadata)` in an item condition fails with `MSB4096` when some items lack it** (`ProjectReference` items without `ReferenceKind`). Qualify it (`%(_OdinOdinRef.ReferenceKind)`) or use `WithMetadataValue`.
- **Compiling against `Microsoft.VisualStudio.ProjectSystem.dll` pulls in more VS assemblies**: using `IProjectThreadingService`-adjacent types gave CS1705 for `Microsoft.VisualStudio.Threading` 18.7 and then `System.Threading.Tasks.Extensions` 4.2.4; both are referenced from VS's `PublicAssemblies` (`Private=false`) with the NuGet compile assets excluded, like `System.Collections.Immutable`.
- **`IVsProjectReference` is COM**: read it after `ThreadHelper.JoinableTaskFactory.SwitchToMainThreadAsync()`; the VSTHRD010 analyzer is an error here.
- **VS keeps the new `ProjectReference` in memory until the project is saved or built**; the file on disk did not change right after the dialog closed.

## Library builds and linking with odin dev-2026-10 (M6, 2026-11-11)
- **`-extra-linker-flags` is split on spaces and ignores quotes.** A path like `C:\my work\x.lib` becomes two flags (`Invalid flag: ace\`, `unable to find library`). odin-vs passes a library path relative to the project folder when the full path has spaces and reports ODIN0107 when it still has any. The default linker here is radlink (`Warning(055): RADLINK`).
- **A library on the link line needs a `foreign` declaration, not a `foreign import`.** `-extra-linker-flags:/LIBPATH:<dir> /DEFAULTLIB:Lib.lib` (quote the whole flag as ONE command-line argument: unquoted, the OS splits it and odin says `Invalid flag`) plus a bare `foreign { name :: proc "c" (...) --- }` links and runs (checked 2026-11-11); `foreign import _ "..."` is a syntax error; with no declaration the call is `Undeclared name`. `foreign import x "system:Lib.lib"` also works (resolved through `/LIBPATH`).
- **`-build-mode:dll` writes `Name.dll`, `Name.lib` (import library) and `Name.pdb`;** the exe needs the DLL next to it (the SDK copies it).
- **`-build-mode:lib` / `static` / `obj` do not produce a `.lib` on Windows with this build:** per-package `Name-*.obj` files are left in the output folder and the link ends with `unresolved symbol 'mainCRTStartup'` (also with `-linker:lld`, `-no-crt -no-thread-local`, `-no-entry-point`). Only the DLL works; re-test on every Odin bump (the tier-3 test `ALibraryProjectAsksOdinForAStaticLibrary` pins the flag, not success).
- **One ols process has one collection set.** See the findings in `docs/milestones.md` (M6, "ols receives collections"): it reads `collections` once from `initializationOptions`; extra workspace folders, `ols.json` files and `didChangeConfiguration` do not change it; a duplicate name takes the last entry.
